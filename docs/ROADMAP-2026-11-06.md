## 0. 先把事实校准

这不是一个"有用户规模的商业 App"。它是**单人维护、自用 sideload、单设备、无账号、无后端、无变现**的 A 股/港股/美股盯盘工具。所以本报告做了三处翻译，否则结论会全是错的：

| 模板假设 | 你的实际 | 翻译后的问题 |
| --- | --- | --- |
| 团队规模 | 1 人 | 每个方案按"每周还剩几小时"折算，不按"业界最佳实践"折算 |
| 商业指标 | 无 | 换成"日常可用性 / 维护成本 / 数据新鲜度" |
| 有灰度用户 | 无 | 没有用户帮你发现 bug；**回归成本低（装回旧包），发现成本高**，优先级偏向"能被自动断言的东西" |

现状快照（全部实测）：

| 项 | 值 | 判读 |
| --- | --- | --- |
| Flutter / Dart | 3.47.9 stable / 3.13.7 | **已是 2026-11 最新 stable**，升级不是杠杆 |
| AGP / Gradle / JDK | 9 / 9.3.1 / 21 | 已在新工具链上 |
| compile / target / min | 37 / 37 / 24 | 已吃满 Android 17 基线，且是自己钉的 |
| APK | 7.84 MB（.so 占 94.3%） | 已到引擎硬成本，见 §1.3 |
| 冷启动 / 滚动 / 内存 | 403ms 中位 / raster 4.1ms@120Hz jank 0 / PSS 112MB | 全部在预算内 3× 以上 |
| 代码 / 测试 | 44 文件 10,298 行 / 44 个测试文件 + analyze 0 | 工程纪律高于同规模项目 |
| 分发 | sideload，单机单用户 | Play 政策（targetSdk 37 / 16KB 页）**不构成约束** |

**三条判断原则**（后面每一条建议都从这里推）：

1. **平台基线是硬约束，框架新特性是软收益。** 前者不跟会突然坏（自适应、内存上限、Activity 重建）；后者不跟只是少个功能。所以"必须升级"只给前者。
2. **自用项目里，可断言 > 可观测 > 可优化。** 你已经没有性能优化空间了（§1），剩下来的是"坏了要知道"和"不再变坏"。
3. **单人项目里，任何"为未来预留的结构"都是负收益。** 除非那个未来在 90 天内会到。

# 第一部分：分层技术升级路线图

## 1. 性能与工程效能

**总判断**：这个维度已经没有"优化空间"，只剩"守住"和"可观测"。冷启动余量 3×、滚动 jank 0、体积到引擎底、静置 12ms 已被归因为 Impeller 的 backdrop 机制（无害，不改）。所以本节的重点从"更快"转成"坏了能知道"。

### 1.1 【必须】把 Android 17 的 per-app 内存上限纳入退出归因 —— ✅ 2026-11-06 已落地

- **落地方式（与原计划的差别）**：原稿写"Kotlin 侧读 + MethodChannel"。实际用 **`package:jni` 直接从 Dart 调 Java**，**零 Kotlin 代码**：`lib/utils/exit_diagnostics.dart`。理由不是"新所以好"，而是 `libdartjni.so` 本来就在包里（path_provider 经 jni_flutter 带进来的），边际成本≈0，而 MethodChannel 要维护「Kotlin + Dart + 通道名」三处。
- **解决什么问题**：Android 17 起系统按设备总 RAM 给每个 App 设内存上限，超限**直接杀进程、不留常规堆栈**（退出原因记为 `REASON_OTHER` + 描述含 `MemoryLimiter:AnonSwap`）。PSS 112MB 离 4GB 机型红线（约 1.5GB）还有 13 倍，短期不会触发；但机器常态可用内存只有 ~300MB、`erm_reclaimd` 占 20–30% CPU，被 OPPO 自家回收策略干掉是真实事件——Flutter 侧对此**完全看不见**。
- **实现要点**：① 判断顺序反过来会失效——`MemoryLimiter` 走的是 `REASON_OTHER` + 描述匹配，必须先判描述；② 首帧之后读（`addPostFrameCallback`），**不进冷启动关键路径**；③ 正常退出（含 sideload 换包 `reason=16`）不说话，只在"死得不体面"时打一行 W。
- **成本**：S（实际约 1.5 小时，含 9 条单测与真机验证）
- **收益**：诊断价值 >> 性能价值。把"莫名白屏/重启"变成一行可归因的日志。
- **前置与风险**：`getHistoricalProcessExitReasons` 是 API 30+，minSdk 24 必须版本分支（且要在任何 `forName('.../ApplicationExitInfo')` 之前判，否则低版本 ClassNotFound）；无需权限。**JNI 的真实代价**：方法签名是字符串，编译器不校验，写错只在运行时抛 `NoSuchMethodError`——所以每个引用都 finally 释放、整体被 try/catch 兜住。
- **实测证据**：`JNI_DEBUG=true` 的 release 包在 PLJ110 上打出 `sdkInt=37 → manager=true → exitRecords=1 → reason=16 desc=stop supermarket.app due to killDueToPackageUpdate`；去掉开关后正常启动**零噪音**；冷启动 353/369/452ms（基线 403ms，无退化）。

### 1.2 【必须】把"升级 Flutter 前测什么"固化成 SOP

- **建议**：写进 README 的三条验收：① 玻璃组真机截图 vs 上一版 `tool/pngdiff.py` 分段比对；② 冷启动同源 A/B（已有 `perf_bench.sh`）；③ 静置 12ms/帧是否仍成立。
- **为什么是现在**：Flutter 3.47 有一条破坏性变更——**OpenGL ES 的 render-to-texture 改为 top-down 存储，自定义 fragment shader 的采样会翻**。你的核心视觉资产 `liquid_glass_widgets 1.16.1` 是纯 GLSL、零依赖，正好踩在这个面上。PLJ110 走 Vulkan 大概率不受影响，但"只有一台机器可测"时，"大概率"不是保证。另外 Impeller 在 3.47 仍是默认开启、opt-out 仍生效但已打 Action Required 警告——意味着未来某个版本会移除，你的玻璃组要有"没有 Skia 也能看"的底。
- **成本**：S
- **收益**：工程效率。每次升级不再从零想"该测什么"。
- **前置与风险**：无。这是流程不是代码。

### 1.3 【必须，收尾】体积到此为止，改成预算断言

- **建议**：`tool/verify_apk.py` 里加一条"APK ≤ 9MB"的断言，并在注释里写死结论：7.84MB 中 7.4MB 是三个 .so，再往下只有"删功能"和"换引擎"。
- **解决什么问题**：不是为了变小，是为了**未来的你加依赖时当场知道代价**。你已经做过五件事（R8、shrinkResources、单 ABI、资源剔除、字体子集），天花板 0.5MB。
- **成本**：S / **收益**：防回退 / **风险**：无。

### 1.4 【探索，低优先】R8 Configuration Analyzer —— 一条被高估的杠杆

- **现实**：Android 17 的官方叙事把 R8 说成最大杠杆（Monzo：冷启动 -30%、ANR -35%、体积 -9%），但那是对**原生 Kotlin/Java 为主体**的 App。你的业务代码全在 Dart，**完全不经过 R8**；Java/Kotlin 侧只有 `MainActivity` + `path_provider` 的壳。能优化的上限是几十 KB 和几毫秒。
- **结论**：花半天跑一次评分可以，别指望数字。真正卡住 R8 的是 `flutter.jar` 的全量 keep——那条**不能动**，动了就是 JNI 找不到符号、release 才闪退。
- **成本**：S / **收益**：≈0 / **风险**：收窄 keep 规则 → 只在真机 release 复现的崩溃。

### 1.5 【跳过】协程/线程模型重构

单 isolate + 3s 轮询 + 生命周期暂停，没有后台线程，没有 isolate 通信。引入 `Isolate.run` 或 compute 只会增加复杂度。唯一的并发（目录抓取 6 路）已经实测到最优点。**不做的代价：0。**

## 2. UI 与自适应体验

先说清楚：你的 UI 层是 **Flutter 不是 Compose**。Compose 1.11 的 Grid/Flexbox/MediaQuery/Style、Navigation 3 的 Scene decorators、Jetpack AppState 全部**不适用**——这里列出来是为了明确"不适用"，不是遗漏。Flutter 里的等价物是 `LayoutBuilder` / `MediaQuery` / 自定义 Router。本节只写三件在你这个栈里真实成立的事。

### 2.1 【必须】Android 17 强制大屏可调整尺寸 —— 唯一"不做会坏"的 UI 项

- **事实**：targetSdk 37 起，sw>600dp 的屏幕上 `screenOrientation`、`resizeableActivity=false`、`min/maxAspectRatio`、`setRequestedOrientation()` 全部被忽略；Android 16 给的临时 opt-out 已被移除（游戏除外）。此外 Android 17 还改了默认行为：`CONFIG_KEYBOARD` / `CONFIG_NAVIGATION` / `CONFIG_TOUCHSCREEN` / `CONFIG_COLOR_MODE` 不再重建 Activity，改为 `onConfigurationChanged()` 下发。
- **你的暴露面**：你没锁方向（对的），Manifest 的 `configChanges` 也覆盖了 orientation/screenSize，所以**不会崩、不会重建**。但布局是**按 1256×2760 单列竖屏调**出来的——横屏/分屏下，玻璃组的 backdrop 尺寸、K 线图宽高比、详情 sheet 高度都会走进没验证过的分支。
- **建议**：三种窗口各截一张基线图——① 竖屏全屏 ② 分屏上半（~1256×1300）③ 横屏（2760×1256）。只修"看起来坏了"的，**不重做设计**。横屏最合理的形态是左列表右图，但那是"想要"不是"必须"，先保证不坏。
- **成本**：M（半天到两天，取决于横屏要不要做双栏）
- **收益**：通过平台基线；顺带解锁分屏盯盘（真实场景：一边看盘一边干别的）
- **前置与风险**：`configChanges` 已含 orientation，Flutter 侧全靠 MediaQuery 自适应；若做双栏，详情 sheet 要能降级成内嵌面板。
- **进度（2026-11-07）**：构建链已对齐（compileSdk / targetSdk 37，AGP 9.2 / Gradle 9.4.1 / JDK 21）；
  布局底线已固化成回归用例 `test/big_screen_layout_test.dart`（竖屏 / 横屏 / 分屏 / 平板 / 气泡
  五个尺寸 + 横屏开弹层，共 6 条，守「不溢出、卡片 ≤560、弹层内容 ≤520」）。
  **仍未做**：三窗口真机截图基线、横屏双栏、折叠屏展开态。
  逐条判定与实测数据见 `docs/ANDROID17-ALIGNMENT-2026-11-07.md`。

### 2.2 【探索，S】输入法 composing 区间

- **问题**：搜索的 250ms 防抖解决的是"请求太密"，没解决"拼音还没上屏就发请求"。中文输入法在 composing 状态下 `onChanged` 会带未确定的拼音——搜"茅台"时可能先拿 `mao` 查一次。
- **建议**：`TextEditingValue.composing.isValid` 时不发请求，等上屏。3 行代码。
- **成本**：S / **收益**：体验（少一次无意义往返和列表闪动）/ **风险**：不同输入法 composing 行为不一致，要用 `isComposingRangeValid` 兜底。

### 2.3 【探索，S 起】Android 17 App Bubbles / 交互式 PiP

- **是什么**：Android 17 允许从 launcher 长按任意 App 变成气泡；桌面模式下 PiP 从"只读"变"可交互"。
- **为什么是你的 App**：盯盘本质是"一直有一条信息在视野里"，气泡比全屏更贴合。
- **现实**：App Bubbles 是**系统行为，长按即可，不需要改代码**——但要能承受极小窗口下的布局。interactive PiP 要原生进 PiP + Flutter 在 PiP 里 resize，**没有官方 Flutter 插件**。
- **建议**：先测"零成本的那半"（长按图标 → 气泡 → 看布局坏不坏），坏了再决定要不要投 PiP。
- **成本**：S 起 / **风险**：Flutter 在极小窗口下 DPR 与宽高剧变会触发全量 relayout，玻璃组 blur 半径按 dp 算可能过重。

## 3. 端侧智能与 AI 集成

**总判断**：这个 App 的"智能"需求是**数据新鲜度和信噪比**，不是生成式能力。所以本节大部分是"明确不做"，只有一条真值得做（§3.3 是体验项，§3.4 是认知项）。

### 3.1 【现在跳过】AppFunctions / Android MCP

- **现状**：平台 API + 对应 Jetpack 库处于 **alpha**；Android 16+ 可用；Gemini 侧集成是私有预览（需 EAP 申请）；调用方需要 `EXECUTE_APP_FUNCTIONS` 权限。
- **对你的收益**：≈0。AppFunctions 的价值是"让第三方 agent 发现并调用你"——你没有分发、没有第三方用户、agent 生态还在私测。唯一价值是练手。
- **如果非要碰**：给 1 天时间盒，只暴露 `getQuote(symbol)` 一个 tool，用官方 test agent app + adb 验证"能被发现、能执行"，然后停。**不要进生产**：alpha API 会变，且会把 Kotlin 层变成一个你半年后看不懂的模块。
- **不做的代价**：0。**成熟度：Alpha → 只做原型，不做集成。**

### 3.2 【跳过】端侧 LLM 做"异动解释"

- **为什么不成立**：解释异动需要**事实**（公告、新闻、板块联动），端侧 1–3B 模型没有这些数据，只会编；换云端 API 又要把自选列表传出去（数据最小化倒退），还要为每次刷新付钱。
- **更有效的替代**：规则化异动提示——涨跌幅/量比/换手阈值 + 本地通知。零模型、零延迟、零成本。见 §A3。

### 3.3 【探索，S】系统 ASR 做"语音加自选"

- **路径**：`RecognizerIntent` / 输入法语音 → 文本 → 复用已有的 `symbol_search`（东财 suggest）模糊匹配 → 加入自选。**不需要端侧模型**。
- **成本**：S / **收益**：体验（走路、开车、手上有事时）/ **风险**：中文股票名 ASR 识别率（"长鑫科技"容易听成"长新科技"），靠 suggest 的模糊匹配兜住。

### 3.4 【必须（认知层）】把"混合推理路由"翻译成你已经做过的事

- 你已经有新浪/腾讯/东财三源 + 连续 3 次失败切换 + 30s 退避上限。这在 AI 语境里就叫"路由 + 降级"，**你已经做完了**。别被新词骗着重写一遍。
- **可升级的一点**：现在的路由粒度是"整个源"，可以细化到"按端点失败率"——报价快、K 线慢，一个源可能只坏一条链路。并把"每源 p50 延迟 / 陈旧率"记成指标，用数据决定切换阈值，而不是固定 3 次。
- **成本**：S–M / **收益**：数据新鲜度（你的核心指标）/ **风险**：指标要先有基线，否则就是换个数字拍脑袋。

## 4. 安全、身份与隐私

**总判断**：没有账号、没有云端、没有埋点，安全面小到只剩"签名"和"网络"。Passkey 这一整块在这里**没有落点**——这不是省略，是结论。

### 4.1 【不适用】Passkey / Credential Manager

- **为什么无落点**：Passkey 解决的是"账号体系的认证强度与转化率"。你没有账号，也没有注册漏斗，"对转化率的影响"无从谈起。
- **什么时候会需要**：如果你做"自选跨设备同步"。那时的正确顺序是 Credential Manager + Passkey（免密码、可随 Google 账号同步），**不是**自建邮箱密码。成本 L。
- **不做的代价**：0。

### 4.2 【必须，S】把签名身份做成可断言的事实

- **现状**：release keystore 在本地、`keystore.properties` 已 gitignore、正式密钥已切——这几步是对的。
- **缺的**：没有任何地方记录"这个包的签名指纹应该是多少"。一旦换机重装或把 APK 发给别人，签名不一致的表现是"装不上/覆盖失败"，而不是一条清晰的错误。
- **建议**：`apksigner verify --print-certs` 的 SHA-256 写进 `verify_apk.py` 断言 + README；每次 release 打一行。
- **成本**：S / **收益**：防替换、防自己踩坑。

### 4.3 【必须，S】显式声明"只走 TLS" —— ✅ 2026-11-06 已落地

- **先纠正初版报告里的一个错误判断**：原稿写"Manifest 里没有 `networkSecurityConfig`，等于默认允许明文"。**这是错的**——`targetSdk ≥ 28` 时平台本来就默认 `cleartextTrafficPermitted=false`。所以加这份配置**不改变今天的运行时行为**，它的价值是"把平台默认写成仓库里可审查的决定"。
- **更要紧的一条（初版没写）**：`network_security_config` 由平台的 HTTP 栈（HttpURLConnection / OkHttp / Cronet / WebView）执行，而本 App 的行情请求走 `dart:io` 的 `HttpClient`——它自带 BoringSSL 与裸 socket，**不经过 NetworkSecurityPolicy**。也就是说：这份 XML 对行情请求**一行都不生效**。
- **所以落地的其实是两件事**：
  1. `android/app/src/main/res/xml/network_security_config.xml` —— `base-config cleartextTrafficPermitted="false"`，Manifest 挂 `android:networkSecurityConfig`。管原生侧（现在是空壳，将来可能有 WebView 或走 OkHttp 的插件）。
  2. `lib/services/rest_client.dart` 的 `requireHttps()` —— 在 `defaultHttpGet` / `defaultHttpGetBytes` 发起请求**之前**拒绝一切非 https 的 Uri。这才是对行情链路真正生效的闸门。抛 `ArgumentError` 而不是吞掉：写错 scheme 是编码错误，不该被当成一次可重试的网络失败。
- **证据**：`test/transport_security_test.dart` 8 条（先红后绿：5 红 → 8 绿），含"lib/ 下不允许 `http://` 字面量 + 合成反例"的静态守门；`tool/verify_apk.py` 新增一条 `传输 ✓ 禁明文配置（清单已挂，cleartext=false）`，从二进制清单与缩短后的资源（`res/8G.xml`）里解出真实取值——**源码写了但没挂上，只有这里看得出来**。真网探针 `PROBE_ROUNDS=2 flutter test tool/polling_live_probe_test.dart` 通过，4 只票实时价正常。
- **成本**：S（实际约 1 小时，含测试与脚本）/ **收益**：把"碰巧都是 https"变成"非 https 发不出去"+ 可审查的配置
- **残留缺口（不假装没有）**：`dart:io` 的 `HttpClient` 默认跟随重定向，且没有"禁止降级到 http"的开关。若某源返回 `301 https → http`，闸门拦不住。三个源目前都不重定向，先按现状接受，别提前加复杂度。

### 4.4 【跳过】存档加密 / 生物识别锁

存的是自选列表 + 股票目录（<200KB），不是敏感数据。加生物识别只会让"抬眼看一下行情"多一步，**直接伤害核心体验**。不做的代价：0。

## 5. 跨设备与系统级集成

**总判断**：这是你**唯一有明显增量价值**的方向——因为盯盘的第一需求是"不打开 App 也能看到"。

### 5.1 【建议做，M】桌面微件（Glance）

- **为什么是你的 App**：4 只票 + 涨跌 + 更新时间，正好是一屏微件的信息量。对自用工具，这等于"每天少点 10 次图标"。
- **现实约束（必须先想清）**：微件刷新受系统节流，`updatePeriodMillis` 最小 30 分钟且不保证。**微件做不了 3s 实时**，只能做"App 在前台时 push 最新快照 + 显示数据时间戳"。没想清这点就会做出一个"永远比 App 旧 20 分钟"的微件。
- **两条实现路径**：
  - Kotlin + Glance：可控、无第三方依赖，但等于维护第二套 UI。
  - `home_widget` 社区包：Dart 侧写数据、原生侧画 RemoteViews，省事，但打破你现在的"零第三方 UI 依赖"。
  - 倾向 Glance：因为 Glance 已统一 phone / Wear / car，是未来唯一不用重写的接口。
- **成本**：M（2–5 天）/ **收益**：使用频率（本节最高）/ **风险**：微件的"旧数据"观感比"没有微件"更差——要么带时间戳，要么只在交易时段显示。
- **成熟度**：Glance 稳定可用；**RemoteCompose 仍是 alpha（1.0.0-alpha06）**，不要为"更花哨的微件"去碰。

### 5.2 【现在跳过】RemoteCompose 的"一次构建、多端呈现"

- **事实**：1.0.0-alpha06（2026-03），入口是 Glance / Wear Widgets，**Flutter 侧没有任何集成路径**。对你要重写一套 Kotlin UI 才能吃到，收益是"微件更花哨"。
- **成熟度判定**：Alpha → 可作为周末原型，**直接跳过生产**。

### 5.3 【跳过】Wear OS / 车机

你没表、没车机、也不打算分发。任何"为多端预留结构"在单人项目里都是负收益。唯一例外：哪天换车且车机支持 Android Auto，5.1 选 Glance 的复用价值会兑现——这是为未来留的**唯一**一个接口。

# 第二部分：新技术头脑风暴清单

## A. 端侧 Agent 与系统级自动化

**A1 · AppFunctions 暴露 `getQuote`**
- 改变环节：用户路径（从"开 App 找票"变成"对助手说一句"）
- MVP：1 天时间盒。Kotlin 侧 `@AppFunction(isDescribedByKDoc = true)` + 官方 test agent app + adb 调用，验证"发现 → 执行 → 回传"闭环即可。
- 不采用的最大代价：**0**（自用无分发、生态私有预览）。判定：只做原型练手，不做集成。

**A2 · 语音/自然语言加自选（系统 ASR，不是端侧 LLM）**
- 改变环节：用户路径
- MVP：2 天。`SpeechRecognizer` → 文本 → 现有 `symbol_search` 模糊匹配 → 预览确认 → 入自选。
- 不采用的最大代价：每次加自选多花 5–10 秒手动输入。判定：可做，S。

**A3 · 规则化盯盘提醒（阈值 + 本地通知）**
- 改变环节：使用方式（从"我去看"变成"它叫我"）
- MVP：1 周。涨跌幅 / 量比阈值 + `NotificationCompat` + 交易时段门控 + 每日去重。
- 不采用的最大代价：**必须一直盯着屏幕，错过异动**——这是全清单里唯一一条"不做真的会损失"的。判定：建议做，优先级仅次于微件。

## B. 状态与逻辑复用（Compose 架构层延伸的 Flutter 等价物）

**B1 · 把"源健康 + 新鲜度 + 退避"收敛成一个显式状态机**
- 改变环节：架构
- 现状：三个正交维度分别散在 `quote_freshness` / `polling_quote_feed` / 页面 `setState` 里，胶囊文案和颜色是这几者的组合推导——组合数一多就容易出现"显示不一致"。
- MVP：1 周。定义 `sealed class FeedStatus { live, stale, switching, backoff, offline }`，把 44 个测试里挑 6 条改成状态断言（先红后绿）。
- 不采用的最大代价：状态组合爆炸导致 UI 文案/颜色说谎（比崩溃更难发现）。

**B2 · KMP 共享状态机**
- 改变环节：架构
- 判定：**跳过**。你已经是 Flutter（本身就是跨端），KMP 是重复投资；且没有 iOS/桌面端需求。不采用代价：0。

**B3 · 轮询生命周期与 UI 解耦（App 级 vs 页面级）**
- 改变环节：架构 / 体验
- MVP：1 周。测"分屏 / 旋转 / 气泡切换后是否重新拉一次、是否出现 3s 空窗"。
- 不采用的最大代价：窗口变化后短暂无数据（你现在 `configChanges` 不重建，风险已被压小，但没验证过）。

## C. 跨设备统一微件与 RemoteCompose

**C1 · Glance 微件（手机主屏）**
- 改变环节：用户路径 / 留存
- MVP：1 周。4 只票 + 涨跌色 + 数据时间戳 + 交易时段语义（收盘后显示收盘价，不显示"12 分钟前"）。
- 不采用的最大代价：少一个"抬眼就看"的入口，每天多开 App 十几次。

**C2 · RemoteCompose 的表达力（snapscroll / 粒子 / 自适应布局）**
- 改变环节：呈现
- 判定：**跳过**（alpha06，Flutter 无路径）。不采用代价：0。

**C3 · 微件的"过期语义"设计范式**
- 改变环节：留存（微件可信度）
- MVP：半天，只做决策不做代码：微件永远显示"数据时刻"而不是"多久以前"；非交易时段显示"收盘"而非灰掉；超过 X 分钟无更新直接隐藏数字只留占位。
- 不采用的最大代价：一个说谎的微件比没有微件更伤信任——你会开始不看它。

## D. 无密码认证与 Passkey

**D1 · Passkey 迁移**
- 改变环节：安全 / 转化
- 判定：**不适用**（无账号体系、无注册漏斗）。若未来做云同步，顺序是 Credential Manager + Passkey，成本 L。不采用代价：0。

**D2 · 应用签名指纹作为"设备身份"**
- 改变环节：安全 / 分发
- MVP：半天。`apksigner verify --print-certs` → SHA-256 写进 `verify_apk.py` 断言 + README。
- 不采用的最大代价：换机/分发时签名不一致的排查成本（表现为"装不上"，不告诉你为什么）。

**D3 · 本地数据的可携带性（自选导出/导入 JSON）**
- 改变环节：留存
- MVP：1 天。导出到公共下载目录 + 导入时校验 `code@region` 并去重。
- 不采用的最大代价：**换机/改包名后自选清零**——你已经因为 `applicationId` 变更踩过一次（旧目录跨 UID 读不到）。这是"身份"问题在你这里最真实的版本：不是"你是谁"，是"你的数据跟着谁走"。

## E. 构建期优化（被低估与被高估的杠杆）

**E1 · R8 Configuration Analyzer**
- 改变环节：工程效率
- 判定：**被高估**。Dart 不走 R8，Java 侧只有壳。MVP 半天跑个分可以，别改 `flutter.jar` 的 keep。不采用代价：≈0。

**E2 · Gradle configuration cache + build cache + 只在 tag 跑 release**
- 改变环节：工程效率（"改一行等多久"）
- MVP：半天，实测 release 构建耗时前后对比（同源 A/B，你已有这套纪律）。
- 不采用的最大代价：每次 release 多等几分钟（若你每次都跑 release，这是每天的成本）。

**E3 · 测试选择而非全量**
- 改变环节：工程效率
- MVP：先测一次全量 `flutter test` 的真实耗时（未测）。若 > 90s，再按目录分片 / CI 只跑受影响模块。
- 不采用的最大代价：本地反馈回路变长，最终导致"不想跑测试"——这是单人项目最大的技术债来源。

**E4 · Kotlin 协程编译期优化**
- 判定：**不适用**。你没有协程代码；Dart 侧的 AOT 优化已由 `flutter build --release` 默认完成。不采用代价：0。

# 优先级矩阵

横轴＝实施成本（S ≤ 1 天 / M = 2–5 天 / L > 1 周），纵轴＝对核心指标的影响（核心指标在此定义为：**数据可信度 + 日常使用频率 + 不坏**）。

| | **成本 S（≤1 天）** | **成本 M（2–5 天）** | **成本 L（>1 周）** |
| --- | --- | --- | --- |
| **影响高** | 签名指纹断言 · TLS 显式声明 · 大屏三张基线截图 · 退出归因 · 微件过期语义（决策） | **Glance 微件** · 自适应布局（含横屏双栏）· 规则化提醒 · 状态机收敛 | —（单人项目不该有 L 级高影响项） |
| **影响中** | composing 区间 · 体积预算断言 · 语音加自选 | 轮询生命周期解耦 · 按端点路由指标 | — |
| **影响低** | R8 评分 · Gradle cache · 测试分片 | App Bubbles / PiP 实验 | AppFunctions 集成 · RemoteCompose · KMP · Passkey · 端侧 LLM |

读法：**左上角是"本周就能做完、且真的会感谢自己"的**；右上角是"值得排期"；中间是"顺手"；右下角是"看起来新、但你的栈里没有落点"——这一格不是"以后再说"，是"明确不做"。

# 90 天执行顺序（按每周 2–4 小时折算）

**第 0–30 天：守住基线，零风险加固（全部 S，可并行）**

1. 升级 SOP 落盘（§1.2）+ 跑一次 pngdiff 基线，确认 3.47 下玻璃无翻转。
2. 签名指纹断言进 `verify_apk.py`（§4.2）——半天。
3. `network_security_config.xml` + `requireHttps` 闸门 + 全链路探针复测（§4.3）—— ✅ 已完成
4. 退出归因（§1.1，实为 `package:jni` 直连，零 Kotlin）—— ✅ 已完成
5. 三种窗口截图（§2.1 第 1 步），只记录不修——半天。
6. **验收**：analyze 0 / 全量测试绿 / 新断言先红后绿留证据（沿用你现有门禁）。

**第 30–60 天：把"不坏"变成"好用"**

1. 自适应布局真修（§2.1）：分屏不裂、横屏不挤；双栏作为可选项，时间不够就砍。
2. 状态机收敛（B1）：sealed `FeedStatus` + 6 条断言。
3. 微件技术选型 spike（C1）：Glance 还是 `home_widget`，用 1 天做一只票的最小版，看刷新节流下的实际观感再定。
4. composing 区间 + 体积预算断言（§2.2 / §1.3）——顺手项。

**第 60–90 天：增量价值**

1. Glance 微件落地（4 只票 + 过期语义 C3），这是本季度唯一"每天都会用到"的新东西。
2. 规则化提醒（A3）：阈值 + 通知 + 时段门控。
3. 决定是否做语音加自选（A2）与导出/导入（D3）——两者都是 1 天级，看剩余精力。
4. **季度复盘**：重跑一遍性能基线（冷启动/滚动/静置/PSS），确认没有因为微件和状态机回退。

# 明确不做（同等重要）

- **不为了 I/O 的新词重写架构**：AppFunctions（alpha）、RemoteCompose（alpha06）、KMP、端侧 LLM、Passkey——你的栈里没有落点，或成熟度不够进生产。
- **不追 Compose 生态**：你是 Flutter，Compose 1.11 / Nav3 / AppState 的收益你拿不到，抄概念只会造出一个"四不像"。
- **不动包体积**：7.84MB 已到引擎底，再压只能删功能。
- **不给自用工具加登录/加密/埋点**：每一步都在伤害"抬眼就能看"这个唯一的核心体验。
- **不为多端预留结构**：没有第二台设备之前，任何抽象都是成本。

---

*一句话：你缺的不是新技术，是"下一次系统或引擎变更时不会静默坏掉"的那层断言。90 天里真正的新增能力只有一个——微件；其余全是防守。*
