### 0.2 假设与缺口（明确标注，且说明影响）

| # | 假设/缺口 | 对结论的影响 |
| --- | --- | --- |
| A1 | 目标设备只有这一台 arm64（你的 PLJ110）；不存在 32 位或 x86 用户 | 32 位剔除的决策已成立。若将来要发给别人，需重跑决策树（§1.4.6） |

### 0.3 三句话结论

1. **体积**：16.59MB 里 15.59MB（94.3%）是三个 `.so`，其中 11.22MB 是 Flutter 引擎本身——**删代码、压资源、裁依赖的天花板是 0.5MB（3%）**。唯一还剩的大杠杆是「把 .so 改成压缩存储」：实测 deflate 后 **16.53 → 7.80MB（-53%）**，代价是装后占用 +7MB、冷启动需复测。这是本轮唯一值得做的体积项。
2. **功耗**：静置 12.5ms/帧已被 A/B 实验归因为 `BackdropFilter` 的引擎级机制（Impeller 遇 backdrop 层放弃局部重绘），占空比 1.25%，**判定无害、不改**。真正剩下的只有两个产品决策：秒表 1Hz、轮询 3s。
3. **内存**：112MB PSS 对 1256×2760@120Hz 设备属正常水位（仅三缓冲就 ~42MB）。**当前没有已证实的泄漏**；下一步不是优化而是补分项归因 + 设阈值告警。

## 1. 体积优化路线图

### 1.1 归因方法与本次实测构成

先归因，再谈优化。三条命令，从粗到细：

```bash
# ① 分钟级：按类别拆包（本次用的就是这条，不依赖任何构建）
python -c "
import zipfile, collections
z = zipfile.ZipFile('build/app/outputs/flutter-apk/app-release.apk')
def cat(n):
    if n.startswith('lib/'): return 'lib .so'
    if n.startswith('assets/flutter_assets/packages'): return 'assets/包内资源(shader等)'
    if n.startswith('assets/'): return 'assets/其余'
    if n.endswith('.dex'): return 'dex'
    if n.startswith('res/') or n=='resources.arsc': return 'res/arsc'
    return 'other'
a = collections.Counter()
for i in z.infolist(): a[cat(i.filename)] += i.compress_size
for k, v in a.most_common(): print('%-24s %6.2f MB' % (k, v/1048576))
for i in sorted(z.infolist(), key=lambda x: -x.compress_size)[:10]:
    print('%7.2f MB  %s' % (i.compress_size/1048576, i.filename))
"
```

# ② 十分钟级：Dart 侧归因（按 package / library 列出 AOT 快照占比）

**本次实测构成（16.53 MiB，71 个条目）**：

| 类别 | 压缩后 | 占比 | 说明 |
| --- | --- | --- | --- |
| `lib/arm64-v8a/libflutter.so` | **11.22 MB** | **67.9%** | Flutter 引擎（Impeller/Skia + Dart VM），**应用侧不可裁剪** |
| `lib/arm64-v8a/libapp.so` | **4.25 MB** | **25.7%** | 你的 Dart AOT 快照（含 framework） |
| `classes.dex` | 0.40 MB | 2.4% | Java/Kotlin 侧，已过 R8 |
| `assets/flutter_assets` | 0.51 MB | 3.1% | 其中 liquid_glass 着色器 0.29MB、NOTICES.Z 0.09MB、字体 0.12MB |
| `lib/arm64-v8a/libdartjni.so` | 0.13 MB | 0.8% | path_provider 的 jni 桥 |
| `res/` + `resources.arsc` | 0.03 MB | 0.2% | 已 shrinkResources |

**三个 `.so` 全部是 method 0（stored 未压缩）**——AGP 8+ 的默认（`extractNativeLibs=false`，直接从 APK mmap）。这正是 1.4.1 那个 -53% 的来源。

### 1.2 「上传体积 / 下载体积 / 安装体积」到底该盯哪个

| 指标 | 定义 | 本项目是否适用 | 目标值 |
| --- | --- | --- | --- |
| AAB 上传体积 | `flutter build appbundle` 产物 | ❌ 不走 Play，无意义 | — |
| Play 下载体积 | 按 ABI/密度切片后用户实际下载 | ❌ 同上 | — |
| **APK 传输体积** | 你发出去的那个文件大小 | ✅ **唯一有意义的「体积」** | **≤8 MB** |
| **装后占用** | APK + 解压出的 .so + dexopt 产物 | ✅ 次要（手机上多 7MB 无所谓） | ≤25 MB |
| 峰值 RSS/PSS | 运行内存，不是「体积」 | 归第 3 节 | — |

结论：**只优化「传输体积」**。Play 那套「下载体积」概念在没有 Play 的前提下是纯噪音；模板里 `--split-per-abi` 的讨论也因此提前结束（见 1.4.6）。

### 1.3 典型构成基准：判断「大头在哪」

| 应用形态 | libflutter.so | libapp.so | 原生/资源 | 谁是大头 |
| --- | --- | --- | --- | --- |
| 最小 Flutter 空壳（本机同版本） | 11.2 MB | 1.5–2.5 MB | <0.5 MB | 引擎 ~80% |
| **本项目** | 11.22 MB | 4.25 MB | 0.9 MB | **引擎 68% / AOT 26%** |
| 含地图+视频+推送的商业 App | 11.2 MB | 5–12 MB | 15–40 MB | 第三方原生 SDK |

判据：**引擎恒定 11.2MB（Flutter 3.47 arm64 release 的硬成本），任何「体积优化」能动的只有剩下那 5.3MB。** 而剩下 5.3MB 里 4.25MB 是 AOT 快照——它随代码量线性增长，10k 行 Dart 对应 4.25MB 属正常（含 framework 约 2MB）。

#### 1.4.1 【P0】原生库压缩存储 —— 唯一还剩的大杠杆

> **已落地（2026-11-06 09:26）**：APK 16.59 → **7.84 MB**，冷启动无退化（同源 A/B 中位
> +5.5ms，噪声内）。完整数据、方法与两次测量翻车记录见 **§6**。

**诊断依据**：三个 `.so` 在 APK 里是 **stored（未压缩）**，占 15.59MB；实测 deflate-9 后只需 6.86MB（`libflutter.so` 47%、`libapp.so` 38%、`libdartjni.so` 20%）。这一项和「瘦身」无关，只是把「APK 里存压缩流、安装时解压到 /data」这条旧路径打开。

**操作**（`android/app/build.gradle.kts`，加在 `packaging {}` 里）：

```kotlin
packaging {
    // 让 Gradle 用 DEFLATE 存 .so，并在 AndroidManifest 里落 extractNativeLibs=true。
    // 效果：传输体积 -53%；代价：安装时解压，装后占用 +约 7MB。
    // 只对 release 有意义（debug 包本来就没人分发）。
    jniLibs {
        useLegacyPackaging = true
        excludes += setOf(   // 保留现有的两条剔除，别覆盖掉
            "lib/armeabi-v7a/libdartjni.so",
            "lib/x86_64/libdartjni.so",
        )
    }
    resources {
        excludes += setOf("kotlin/**", "kotlin-tooling-metadata.json", "DebugProbesKt.bin")
    }
}
```

**预期收益**：16.53 → **7.80 MB**（估算值 = 16.53 − 15.59 + 6.86；打包器实际压缩率通常差 1–3%，验收时以实测为准）。这是本轮唯一超过 1MB 的项。

**风险与注意事项**：
- 这**不是真瘦身**，是把解压成本挪到安装期。装后占用从 ~16.5MB 升到 ~23–24MB；对自用手机无感，但如果你在意「装完占多少」，这就不是免费的。
- **冷启动必须复测**：不压缩时引擎直接从 APK mmap，压缩后从 `/data/app` 读。理论上差 0–30ms，但你有 403ms 的基线，一定要 A/B，别用「理论上」交差。
- Android 15+ 的 16KB 页要求只管**未压缩**的 `.so`；本包 `zipalign -c -P 16` 已通过，改压缩后这条约束自然消失，但**别把它当成「顺手修好了对齐」**——当前对齐本来就是对的。
- 回滚：删掉那一行，重打包即可；无数据/签名影响。

**验收**：

```bash
python -c "import zipfile;z=zipfile.ZipFile('build/app/outputs/flutter-apk/app-release.apk');print(sum(i.compress_size for i in z.infolist())/1048576,'MB');print([ (i.filename,i.compress_type) for i in z.infolist() if i.filename.endswith('.so')])"
# 期望：~7.8 MB；三个 .so 的 compress_type 从 0 变 8
python tool/verify_apk.py            # ABI/targetSdk 断言必须仍全绿
./tool/perf_bench.sh                 # 冷启动 3 次，与 403ms 比
```

#### 1.4.2 【P1】体积回归门禁（收益是「不再变胖」）

**诊断依据**：当前没有任何一条断言盯着「体积」。`verify_apk.py` 钉的是 targetSdk 与 ABI，不是字节数。而这个应用的增长风险是真实的：加一个 K 线指标库、一个图表库、一个图片缓存，随便就 +0.5MB。

**操作**：在 `tool/verify_apk.py` 的断言列表里加一条硬上限（与现有风格一致：超了当场红）：

```python
MAX_APK_BYTES = 8_600_000        # P0 落地后设 ~8.2MB + 5% 余量；落地前先设 17_200_000
if apk_size > MAX_APK_BYTES:
    fail(f"APK {apk_size/1048576:.2f} MB 超过上限 {MAX_APK_BYTES/1048576:.2f} MB："
         f"先跑 §1.1 的归因，确认新增字节来自哪里，再决定是接受还是改设计")
```

**收益**：0 字节，但把「体积」从事后感叹变成提交时红灯。**风险**：上限设太紧会让正常的版本升级天天红——按「当前值 +5%」设，每次有意增长时手动上调并留一行注释说明原因。

**验收**：故意塞一个 1MB 的假 asset → 脚本红；移除 → 绿。

#### 1.4.3 【P2】字体字重裁剪

**诊断依据**：`assets/fonts/inter-latin-{400,500,600,700}.ttf` 各 ~30KB（压缩后），共 276KB 原始 / 0.12MB 包内。如果主题只用 400/600（`ThemeData` 里 `fontWeight` 的实际取值），500/700 是纯浪费。

**操作**：先查实际用到的字重，再删未用档位：

```bash
grep -rn "FontWeight\.\(w\?[0-9]\+\)" lib/ | grep -o "FontWeight\.[a-z0-9]*" | sort | uniq -c
grep -rn "Inter" lib/ | head
```

只保留出现过的档位，同步删 `pubspec.yaml` 的 `fonts:` 条目。

**收益**：-30~60KB（0.2~0.4%）。**风险**：被删字重若被 TextStyle 继承链隐式请求，会回退系统字体 → 数字宽度变化（本应用大量等宽数字对齐，**这是真实风险**）。**验收**：`test/preview` 的 golden 全绿 + 真机目视价格列对齐。

#### 1.4.4 【✗】排除 liquid_glass 着色器 —— 否决

名义上 `liquid_glass_geometry_blended.frag` 0.24MB + 其余 0.05MB。但依赖台账第三节写明 `GlassContainer(quality: GlassQuality.premium)` 在 `quote_tile.dart` 里正在用，premium 档走的就是这套着色器；包内资源是**运行时按名加载**，排除后不会编译期报错，只会在真机上玻璃退化成白板。收益 1.5%、风险是核心视觉，**不值得**。

#### 1.4.5 【✗】libapp.so 再压 —— 天花板 0.3MB

4.25MB 里约 2MB 是 Flutter framework 自身（`package:flutter`），能动的只有业务代码 + liquid_glass 的 Dart 层。删依赖不现实（视觉核心），拆功能不现实（单页应用）。**结论：不动。** 若一定要量化，跑 §1.1 的第 ② 条命令，看 `package:flutter` 与 `package:super_market` 的占比，再决定要不要为 0.2MB 折腾。

#### 1.4.6 【✗】ABI 策略 —— 已完成，且决策树保留备查

现状：`--target-platform android-arm64`（只出 64 位引擎）+ `packaging.jniLibs.excludes`（剔第三方 AAR 带进来的 v7a/x86_64 `.so`）。`aapt` 实测 `native-code: 'arm64-v8a'` 单架构，48.9MB → 16.6MB 的降幅已在历史里。

必须记一笔**踩过的坑**（`build.gradle.kts` 注释里已有）：`buildTypes.release.ndk { abiFilters += "arm64-v8a" }` **对 AAR 带进来的 `.so` 无效**，只作用于 `ndkBuild`/`jniLibs` 源码目录。真正生效的是打包期 excludes。

**保留 32 位的决策树**（将来若要分发给别人）：

```
要分发给第三方吗？
├─ 否（当前）→ 只出 arm64。理由：minSdk 24 + 2016 年后设备 99%+ 是 arm64
└─ 是
   ├─ 目标市场有一加/红米老机、电视盒子、车机（可能 32 位）吗？
   │  ├─ 有 → 出 armeabi-v7a 变体，用 --split-per-abi 出两个 APK 分开安装
   │  │       代价：v7a 多一份引擎 8~9MB；且 Flutter 3.47 已不支持 32 位 iOS，
   │  │       安卓 32 位仍是 supported，但要接受低端机 jank 明显更高
   │  └─ 没有 → 维持 arm64 单架构
   └─ 走应用商店吗？→ 走商店就出 AAB（bundle 自己按设备切片），
                       但 AAB 只能上 Play；国内商店要 APK，得用 --split-per-abi
```

`--split-per-abi` vs `abiFilters` vs AAB 一句话取舍：**sideload 单机型 → 单 ABI 直接打；多机型 sideload → `--split-per-abi` 出多包；上 Play → AAB。** 三者不叠加使用。

#### 1.4.7 【✗】Deferred Components —— 不适用

判断标准（模板要求）：体积 >50MB **且** 功能模块边界清晰 **且** 分发渠道是 Play（AAB + Play Core 动态下发）。本项目 16.6MB、单页应用、不走 Play——**三条全不满足**。强行接入只会引入 Play Core 依赖、拆包失败时的降级路径、以及「延迟加载模块首次点击要等下载」的体验坑。**明确不做。**

#### 1.4.8 构建习惯

- `./build_apk.sh` 已是唯一出口（带 `--obfuscate --split-debug-info`），**别直接 `flutter build apk`** 出正式包——会漏掉符号分离。
- 对比构建前后产物：`ls -l` 不够，用 §1.1 的 Python 归因（`ls` 只看总字节，看不出是哪个类别胖了）。
- `flutter clean` 只在「怀疑产物污染」时用（换 Flutter 版本、改 Gradle 插件后）；日常不需要，它会让下次构建多花 3–5 分钟。
- debug 变体混入 release 流程的现有防线是 `verify_apk.py` 的 ABI/targetSdk 断言，**再加一条 §1.4.2 的体积断言即可闭环**。

## 2. 功耗优化路线图

### 2.1 诊断依据：目前只有「推算」，没有「实测」

| 场景 | 帧成本 | 帧频 | GPU 占空比 | 依据 |
| --- | --- | --- | --- | --- |
| 前台静置（收盘） | raster 12.3–12.5 ms | 1 Hz（秒表） | **1.25%** | 基线台账 §3/§7，A/B 四次实验 |
| 前台盘中 | raster ≈12.5 ms（未测，推算） | 0.33 Hz（3s 轮询） | ~0.4% | 需 §2.2 补采 |
| 前台滑动 | raster 4.1–5.3 ms | 120 Hz | ~50%（瞬时） | 基线台账 §2 |
| 后台 | 轮询暂停 | 0 | ~0 | `lifecycle_pause.dart` |

**关键认知（已被 A/B 证实，别重复怀疑）**：静置那 12.5ms 不是「你没优化好」，是 `BackdropFilter` 在 Impeller 下的语义——一旦存在 backdrop 层，**partial repaint 被放弃，每帧全屏重跑模糊**；包进 `RepaintBoundary` 无效（实验④，12.1–12.4ms），换 `quality: standard` 也无效（实验②，成本在 blur 本身不在着色器），而去掉 `GlassBackdropGroup` 反而涨到 18.6–19.3ms（实验③，组省 35%）。**现状已是最优点。**

**缺口**：没有 mA/小时。`dumpsys batterystats` 是唯一能给出「真实耗电」的口径，且必须在两个场景各采 30 分钟。

#### 2.2.2 【P1】轮询自适应 —— 唯一有实际收益的功耗项

**诊断依据**：`AppConfig.pollInterval = 3s`，每分钟 20 次网络 + 20 次可能的重绘，每次重绘在玻璃层触发全屏 blur（12.5ms）。盘中这 12.5ms × 20/min = 每分钟 250ms GPU——单看不吓人，但它是**屏幕常亮期间唯一的周期性 GPU 唤醒**，直接影响 LTPO 面板能否降频。

**操作**（代码级，改动点在 `polling_quote_feed.dart`，约 20 行）：把固定间隔改成「按波动自适应」——

```
收到快照 → 与上一帧比较
├─ 任一标的价格变化 → 下一次 3s（盯盘优先）
├─ 全部无变化，连续 3 次 → 退到 10s（无人动盘口）
└─ 页面不可见 / 后台 → 停（已有 lifecycle_pause，别重复实现）
```

已有的 `shouldApplyQuote`（同值快照不重绘）是「拦重绘」，这个改动是「少发请求」——两者不冲突，叠加后效果最好。

**收益**：静默时段请求量 -70%，GPU 周期性唤醒 -70%。绝对能耗节省取决于屏幕占比，**未测前不给 %/hr**。**风险**：行情突然启动时最多晚 10s 发现（对自用盯盘可接受，但你要认可）；网络层已有 30s 退避上限，不要与自适应逻辑打架（一个管「失败退避」，一个管「无变化降频」，代码上分开写）。

**验收**：`polling_feed_test.dart` 加用例（先红后绿）；真机按 §2.2.1 口径采 30 分钟，对比 mAh。

#### 2.2.3 Isolate 决策表（哪些必须 offload，哪些不值得）

| 场景 | 单次耗时量级 | 结论 | 理由 |
| --- | --- | --- | --- |
| 195KB 股票目录 `jsonDecode` | 10–30 ms（未测） | **取决于是否落在首帧**：冷启动路径 → 用 `compute()`；已缓存后不走 | isolate 冷启动 5–20ms + 一次内存拷贝；<8ms 的活搬过去更慢 |

### 3.1 诊断依据：112MB 是「正常」还是「偏高」

先把参照系摆正。1256×2760 的屏幕，一张全屏 RGBA 缓冲 = 13.9MB；三缓冲 ≈ 42MB，这是**任何**全屏应用的下限。Flutter 引擎自身（Dart heap + VM + code）空载约 40–55MB。再加上：

| 组成 | 本项目实测/推算 | 备注 |
| --- | --- | --- |
| TOTAL PSS | **112 MB** | 基线台账 §4，启动后静置 5s |
| TOTAL RSS | 174 MB | 含共享页 |
| Swap PSS | 42 MB | 说明有部分页被换出，正常 |
| 其中 Graphics | **未测（缺口）** | 玻璃离屏纹理大概率在这；必须补 `dumpsys meminfo` 分项 |
| 其中 Native Heap | 未测 | 引擎 + skia/impeller 的资源 |

#### 3.2.1 【P0】分项归因（20 分钟，必须先做）

```bash
adb shell am force-stop supermarket.app

sleep 8
adb shell dumpsys meminfo supermarket.app | head -40
# 关注：Java Heap / Native Heap / Code / Stack / Graphics / GL mtrack / Private Other

```

读法：
- **Graphics** 高（>40MB）→ 玻璃离屏纹理是大头，3.2.2 才有意义；
- **Native Heap** 持续涨 → 引擎/解码泄漏，查 `am dumpheap`；

#### 3.2.2 【P2】玻璃离屏纹理（条件执行）

只有 3.2.1 显示 Graphics 显著偏高时才做。可动的旋钮（按代价从小到大）：`GlassBackdropGroup` 的共享范围是否可覆盖详情弹层（审查报告 P1-3 指出详情弹层是「整块内容塞进 BackdropFilter」——**这是唯一还没被组化的地方，也是这里最可能的收益点**）；其次才是降档/静态缓存。**在拿到分项数据前不要动手**——上一轮已经用四次 A/B 证明「拍脑袋改玻璃」全是负收益。

#### 3.2.3 【P1】预算与阈值

| 设备档位 | 典型屏幕 | 合理 PSS 区间 | 告警线 |
| --- | --- | --- | --- |
| 低端（3–4GB RAM，720p） | 720×1600 | 80–120 MB | >140 MB |
| 中端 | 1080×2400 | 100–150 MB | >170 MB |
| **旗舰（本机）** | 1256×2760@120Hz | 110–180 MB | **>200 MB** |

泄漏判定（比单点数值可靠）：

```
启动静置 5s → 记 PSS₀ → 盘中 10 分钟不操作 → 记 PSS₁
├─ PSS₁ − PSS₀ < 15MB          → 正常峰值波动，不是泄漏
├─ 15–30MB 且趋于平稳          → 缓存填充，可接受
└─ 持续单调增长（每 10 分钟 +20MB 以上） → 泄漏，进 3.2.5 流程
```

把这三条写进 `tool/perf_bench.sh` 的 `--mem` 分支，跑一次出结论。

#### 3.2.4 Widget 层：这项已经是「已生效」，不是「待办」

模板要求「系统性使用 const 构造器」——本项目 `analysis_options.yaml` include 的 `flutter_lints` **已经包含** `prefer_const_constructors` / `prefer_const_constructors_in_immutables` / `prefer_const_declarations` / `prefer_const_literals_to_create_immutables`（已核对包内 `flutter.yaml`），且 `flutter analyze` 门禁是 0 issue。**所以 const 不是优化项，是既成事实。**

同理：`unused_import`/`unused_local_variable`/`unused_field` 已被提成 error；`ListView.builder` 的使用、`setState` 作用域、helper 方法返回 widget 的问题在审查报告 P1-1/P2-6 已逐条处理。**这一层没有剩余空间**，再投入就是自我安慰。

#### 3.2.5 泄漏排查流程（若 3.2.3 判定泄漏）

1. DevTools → Memory → 连真机 profile 包 → **Snapshot**；
2. 复现路径（开详情 → 关 → 开订阅 → 关）×10 → 再 Snapshot；
3. 对比两次快照的 `Retaining Path`，找「应该被回收但被根持有」的对象（GlobalKey、单例、闭包捕获 context）；
4. 本项目的已知高风险点：`_notifiers`（`quote_list_page.dart:174` 有 `removeWhere` 清理，需验证是否覆盖全部路径）、`KlineLoader._cache`（已设上限）、三个 Timer（均在单页持有，页面销毁需 dispose）。

#### 3.2.6 原生侧内存

本项目 Platform Channel 只传**字符串路径**（path_provider 取目录、文件读写），**不存在大 buffer 跨通道拷贝**的问题。`MethodChannel` 的大数据拷贝风险在本项目无对象。若将来加 `EventChannel` 传 K 线二进制，再考虑 `StandardMessageCodec` 的 `Uint8List` 零拷贝（`binaryMessenger` 直传 `ByteBuffer`）。

### 6.3 测量方法（含两次翻车，下次别再踩）

**翻车① 拿台账数字当对照**。先用基线台账的 403ms 做参照，于是「16.59MB 包」现场测出
1034–1123ms，差点写成「压缩存储拖慢 3 倍」。原因：403ms 是 2026-11-05 22:00
**收盘时段**采的，今天是 09:19 **盘中**（轮询活跃 + 数据重绘）。→ **跨日/跨时段数字不可比。**

**翻车② 单轮测量被设备负载污染**。该机当时 `Mem 11.0G/11.3G used`、`swap 6.9G`、
`erm_reclaimd 29% CPU`、`system_server 32%` —— 系统在持续直接回收，任何单轮 `am start -W`
都是一次随机数。→ **先看负载，再决定这轮数据要不要。**

**可用协议（本次最终采用）**：

```
同源重建两版（只差 useLegacyPackaging 一行）→ 存档 A/B 两个 apk
A→B→A→B 交叉轮测，每轮：
  install -r → 启动一次预热（丢弃）→ 静置 30s → 5 × (force-stop → sleep 1.5 → am start -W)
取每轮中位，再合并 pool 中位；只看区间是否重叠，不看单次快慢
```

### 6.4 判定

**保留。** 差异 +5.5ms（+1.6%），远小于轮内波动（±20ms）与两版区间重叠度，判为**无退化**；
门槛 450ms，最差样本 374ms，余量充足。相对收益是传输体积腰斩——对「发给自己/别人装」
这个唯一场景，值。

### 6.5 副作用、回滚与未验证

- **副作用**：装后占用 +6MB（17→23MB）；首次安装多一次解压（一次性，不在冷启动路径上）。
- **回滚**：删掉那一行 → 重打包 → 回到 16.59MB / 17MB 装后占用。无签名、无数据影响。
- **未验证**：低端机（无设备）上的解压耗时；分批更新场景（不走 Play，无意义）；
  `flush install`（`adb install --fastdeploy`）行为差异。
- **顺手核实**：`mCurrentFocus` 断言在每次采集前都跑了一遍——这次没被别的 App 抢焦点，
  但也确认了「采集前必须确认前台」这条纪律不能省。

### 6.6 对后续测量的提醒（重要）

本次暴露的一个事实：**这台机器常态可用内存只有 ~300MB，`erm_reclaimd` 长期在 20–30% CPU。**
这意味着：

1. 任何性能数字都要「多轮 + 交叉」才可信，单轮结论一律不写进台账；
2. 基线台账里 403ms 与今天 345ms 的差异（同款构建）**不是代码变化**，是设备状态差异——
   以后比较冷启动，优先比「同一时段内的 A/B」，而不是跟历史绝对值比。
