## 一、项目概览

### 项目定位与核心逻辑

个人自用的 Android 前台盯盘 App：**新浪财经主源 + 腾讯财经备源**，3 秒一轮 HTTP 批量轮询（零凭证、无 WebSocket），自选 30 只上限（A/H/美），每只股票一个 `ValueNotifier<Quote>` 局部刷新；详情页自绘分时 / 日 K（主备切换 + 30s 缓存 + 实时价补丁）；液态玻璃视觉（premium 着色器 + BackdropFilter 双路线）。数据层全部落盘到应用私有目录（原子写 + 损坏留档）。

分层：`UI(pages/widgets) → QuoteFeed(轮询状态机) → PollingSource(协议) / KlineLoader → KlineSource(协议)`，组合根 `AppDependencies` 显式注入。协议事实（域名、字段下标、单位换算、Referer）全部隔离在 `lib/services/source/` 内。

## 三、详细分析

### [P1-E01] 两个 commit 之外的全部工作处于未提交状态

- **位置**：仓库状态（`git log` 仅 `b3d13f4` / `2b47d0d`，后者标注 v1.0.1；`git status` 15+ 源文件与 golden 为 Modified）
- **现象 / 触发条件**：v1.0.1 → v1.0.7+35 的全部代码（美股支持、页头重排、A05/A10 对比度、3.0x 溢出修复、太极改 tick 驱动等）只存在于工作区。
- **根因分析**：项目以「打包即交付」运作，git 沦为初始化时的一次性快照；工作记忆里「项目非 git 仓库」的认知也已与现状脱节。
- **影响范围**：任何一次误操作（`checkout .`、`reset --hard`、误删目录）或磁盘故障都会造成**不可逆**丢失；也堵死了「回滚到某个可装机版本」的能力。
- **复现 / 验证方式**：`git status --short | wc -l` > 0；`git log --oneline | wc -l` = 2。
- **【最佳实践】**：每完成一个通过门禁（analyze 0 + test 全绿）的批次就 commit；版本号 bump 与 commit 一一对应；发布 tag（`v1.0.7`）指向已验证的打包 commit。配合 GitHub 私有仓库异地备份。
- **【最优方案】**：在【最佳实践】之上加分支纪律：`main` 只收通过门禁的批次，装机验证后再 tag；build 产物与 debug-info 用 release/tag 关联（`build/debug-info` 已有，符号表与 commit 绑定可还原混淆堆栈）。成本：每次打包多 2 分钟；收益：任何版本可复现、可回滚；风险：无。
- **【最小方案】**：现在立即做一次快照 commit（消息注明 v1.0.7+35），此后每版打包前 commit 一次。不建远程、不开分支。技术债：仍无异地备份，回滚粒度粗。
- **推荐选择及理由**：先执行【最小方案】（一次 commit 立刻消除丢失风险），随后按【最佳实践】养成批次 commit 习惯；个人项目不需要【最优方案】的完整分支纪律。

### [P3-C01] 同一秒内的第二次报价被丢弃

- **位置**：models/quote.dart:262-266（`shouldApplyQuote` 同刻分支）
- **现象 / 触发条件**：新浪时间戳粒度为秒。同一秒内出现两笔不同价的报文时，第二帧与当前帧 `isAtSameMomentAs` 且同为 `socket`，返回 false 被丢弃。
- **根因分析**：同刻冲突规则的判据是「来源可信度」（实时>快照），而不是「价格是否真的变了」；对轮询链路（所有报价都标 socket）来说，同刻即丢弃。
- **影响范围**：极端高频成交下，卡片价格比实际晚一个轮询周期（≤3s）更新；无错误数据，只是滞后。
- **复现 / 验证方式**：单测——构造两个 `Quote`（同 timestamp、不同 price、均 `QuoteSource.socket`），`shouldApplyQuote(first, second)` 返回 false。
- **【最佳实践】**：同刻比较改为「内容优先」：价格/成交额任一变化即接受，仅完全重复的帧才丢弃（`Quote` 已实现 `==`，一行 `incoming != current` 即可表达）。
- **【最优方案】**：在【最佳实践】之上给 `Quote` 加单调递增的本地序号（feed 层赋值），同秒冲突按序号裁决——彻底摆脱「时间戳粒度」这个外部约束。成本：模型+feed 各改一处，需同步调 `_lastQuoteMs` 语义；收益：任何粒度的时间戳都不丢新价；风险：改动触及防倒退核心逻辑，须先红后绿补回归。
- **【最小方案】**：同刻分支加一条：`incoming.source == current.source && incoming != current` 时也放行（内容变了就不是重放）。技术债：`_lastQuoteMs` 的「防切源倒退」仍按时间戳工作，同秒回退价理论上仍可能穿过（该守卫在 feed 层挡）。
- **推荐选择及理由**：【最小方案】。3s 轮询下用户可见收益很小，但一行改动零风险消除「重放帧挡新价」的误伤；【最优方案】的序号体系在这个数据频率下属于过度设计。

### [P3-C05] 订阅判重依赖 name，同名漂移可产生重复卡

- **位置**：widgets/watchlist_sheet.dart:225（`_stocks.contains(stock)`）+ app_config.dart:57-62（`==` 含 name）
- **现象 / 触发条件**：存档里的名称与搜索接口返回的简称不一致（公司更名、简称调整、搜索源与目录源不同步）时，同一 `code@region` 被视为「未订阅」，可再次添加。
- **根因分析**：`StockConfig.==` 刻意让 exchange 不参与判重（注释已论证正确），但 name 参与了——而 name 本质是**展示数据**，会漂移；身份应是 `code@region`。
- **影响范围**：列表出现两张同价卡（同一 notifier）；重启后 `decode` 的 `seen` 去重自愈；不会写坏数据。
- **复现 / 验证方式**：单测——存档 `[000651@SZ 名"格力电器"]`，`_add(StockConfig(code:'000651', region:'SZ', name:'格力电A'))` → 不报「已在列表」，成功加入。
- **【最佳实践】**：订阅判重统一用身份键 `stock.key`（`_add` 里改 `any((s) => s.key == stock.key)`）；`==` 中 name 仅用于展示比较场景。
- **【最优方案】**：同【最佳实践】（此问题足够小，方案无分层差异），并把 `StockConfig.==` 收窄为 code+region——name 漂移时 notifier/存档比对也更稳。成本：改 1 行 + 检查 4 处依赖 name 相等的调用点（`_openWatchlist` 的 `_sameStocks`、decode 判重均已按 key）；收益：身份语义彻底单一；风险：极低，回归测试覆盖 `_sameStocks` 即可。
- **【最小方案】**：只改 `_add` 一处判重为按 key。技术债：`==` 的 name 参与仍在，其它潜在比较点不变。
- **推荐选择及理由**：【最优方案】——改动同样是几行级别，且「身份键唯一」与项目既有注释哲学（key 不跟展示属性走）完全一致。

### [P3-R01] LiquidGlassWidgets.initialize 无兜底，失败即白屏

- **位置**：lib/main.dart:40
- **现象 / 触发条件**：`await LiquidGlassWidgets.initialize()` 在 `runApp` 之前执行且无 try/catch；若第三方着色器预热抛错（**待确认**：上游实现是否可能抛，注释称非阻塞 IO），main 中断，App 永远白屏。
- **根因分析**：对第三方初始化的乐观假设（「不拖慢启动」论证了 await 的合理性，但没论证「不抛」）。
- **影响范围**：失败模式下用户只看到白屏，连错误页都没有；logcat 有一条 uncaught。
- **复现 / 验证方式**：单测难以模拟（需 mock 平台通道）；代码级审查即可确证无兜底。
- **【最佳实践】**：所有第三方 SDK 初始化包 try/catch 并降级：初始化失败不影响进 App，最多退化为无玻璃视觉。
- **【最优方案】**：try/catch + `AppLog.e` + 置一个 `glassDisabled` 标记，`LiquidGlassWidgets.wrap` 处按标记降级为直接返回 child。成本：~20 行；收益：第三方库的任何上游回归都不再是「白屏级」事故；风险：降级路径需要一次真机走查（golden 不覆盖）。
- **【最小方案】**：只包 try/catch + AppLog.e，失败继续 `runApp`（wrap 仍执行——若 wrap 依赖 initialize 的内部状态，需验证 wrap 是否独立可跑；**待确认**）。技术债：降级不彻底。
- **推荐选择及理由**：先做【最小方案】（5 分钟消除白屏路径），【最优方案】的降级标记等真机验证过 wrap 独立性再上。

### [P3-R02] KlineLoader 只捕 Exception，与项目自身纪律不一致

- **位置**：services/kline_loader.dart:139（`on Exception`）
- **现象 / 触发条件**：`parseOf(source, res.body)` 若抛 Error 级异常（RangeError、TypeError 等），会穿透 `_load` → 详情页 `_load` 的 await（无 catch）→ 全局钩子记录、UI 永停「加载走势…」。
- **根因分析**：symbol_directory.dart R-04 的教训（「边界层必须连 Error 一起拦」）没有推广到 KlineLoader；两个解析器目前防御到位（长度守卫 + tryParse），所以是**潜在风险**而非现实 Bug。
- **影响范围**：仅详情页走势区块；列表不受影响。
- **复现 / 验证方式**：单测注入一个抛 `RangeError` 的假 httpGet，断言返回 `KlineResult.failed` 而非抛出（当前会红）。
- **【最佳实践】**：网络/解析边界层统一 `on Object`，与 PollingQuoteFeed `_poll`（`on Object catch`）对齐；Error 单独记一条更响的日志。
- **【最优方案】**：同【最佳实践】并补两条回归测试（Error 级解析失败 → failed 结果、Error 级请求失败 → 换下一个源）。成本：半小时；收益：上游接口形状再怎么变都不会把装饰性数据变成挂起页面；风险：无。
- **【最小方案】**：`on Exception` → `on Object`，一行。技术债：无测试钉住，行为可能被静默改回。
- **推荐选择及理由**：【最优方案】——项目门禁本来就要求新断言先红后绿，两条测试的成本本来就是纪律的一部分。

### [P3-U01] 图表 shouldRepaint 漏比样式字段

- **位置**：widgets/kline_chart.dart:920-925
- **现象 / 触发条件**：`shouldRepaint` 只比较 mode/bars/points/prevClose；`axisStyle`（刻度文字样式）或 `hk`/`us`（区域口径）变化时返回 false，图停留在旧样式。
- **勘误（实施时红态取证发现）**：初版报告称「系统字体缩放变化时刻度停在旧字号」——**实测不成立**。`axisStyle` 是 `DefaultTextStyle.style.copyWith(fontSize: 9.5, …)`，fontSize 被 copyWith 钉死，图表整体缩放不变；缩放确实不该触发重绘。真正成立的症状是「axisStyle 里**其它**属性变化（如字体族）或区域口径变化时不重绘」。修复保留，注释与测试都按勘误后的事实书写。
- **根因分析**：painter 字段增加（hk/us 是后加的）后没有同步更新 shouldRepaint 的比较集。
- **影响范围**：样式口径变化后的短暂不一致；缩放场景无影响（图本来就是缩放不变的）。
- **复现 / 验证方式**：单测——两个 painter 实例（同一份 bars、不同 DefaultTextStyle 字体族）之间 `shouldRepaint` 应为 true（修复前 false）；另一条用例钉住「缩放变化 → false」的刻意语义。
- **【最佳实践】**：CustomPainter 的 shouldRepaint 要么比较**全部**影响绘制的字段，要么 painter 做成值对象整体 `==`。
- **【最优方案】**：给 `_KlinePainter` 实现完整 `==`/`hashCode`（含 axisStyle/hk/us），shouldRepaint 返回 `old != this`。成本：~15 行；收益：以后再加字段不会漏；风险：无。
- **【最小方案】**：在现有 shouldRepaint 里补 `old.axisStyle != axisStyle || old.hk != hk || old.us != us`，并配两条用例（真变化 → true；缩放不变 → false）。技术债：下个字段仍可能漏。
- **推荐选择及理由**：【最小方案】（已实施）。图表字段已稳定，完整 `==` 的收益要等字段再变时才兑现；缩放语义用测试钉住比注释更可靠。

### [P3-C03] FileKeyValueStore 并发写存在 .tmp 竞态（潜在风险）

- **位置**：services/local_store.dart:153-158
- **现象 / 触发条件**：`.tmp` 路径固定；同一实例两个 `write` 并发执行时，一方 `rename` 会因 tmp 被对方抢先改名/重写而失败，该次写盘丢失。**待确认**：现实中 watchlist save 与 directory cache write 是否存在同帧并发窗口（当前调用链上两者都各自 await，几乎不重叠）。
- **根因分析**：原子写方案正确（tmp + rename），缺的是「单飞」——同实例写盘串行化。
- **影响范围**：丢一次写盘；内存缓存仍是全集，下一次成功写盘即自愈；最坏情形是「这次改动重启后没保存上」。
- **复现 / 验证方式**：单测——`Future.wait([store.write('a','1'), store.write('b','2')])` 大量重复，断言无异常且两键持久化（当前偶发红）。
- **【最佳实践】**：写路径加互斥（`Future` 链式排队），保证同实例串行。
- **【最优方案】**：同【最佳实践】：`Future<void> _writeLock = Future.value();` 写操作 `return _writeLock = _writeLock.then((_) => _writeAll(data));`，顺带把不同 key 的并发写合并成更少次全量落盘。成本：~10 行；收益：竞态归零 + 写放大减少；风险：写顺序变化需回归 R-02/R-03 两条既有测试。
- **【最小方案】**：tmp 文件名加唯一后缀（`.tmp-${DateTime.now().microsecondsSinceEpoch}`），rename 各自独立。技术债：两个并发全量写仍可能后写覆盖先写（内容是同一份缓存全集，实际无害），写放大仍在。
- **推荐选择及理由**：【最优方案】——排队锁是这类「整文件覆盖」存储的标准解法，代码极小；若无现实并发窗口，也可以先记档不动（触发条件待确认，属低优先加固）。

### [P3-C02] 实例池依赖 VM 的 tear-off 规范化（潜在风险，已实测当前成立）

- **位置**：services/local_store.dart:70（`identityHashCode(provider)`）
- **现象 / 触发条件**：默认构造路径 `FileKeyValueStore()` 每次求值 `getApplicationSupportDirectory` 都是新 tear-off；池 key 用 `identityHashCode`，依赖「同源 tear-off identical」。**已实证**：Dart VM（JIT）上 identical 成立（探针输出 identical=true）；Dart 语言规范仅保证 `==` 相等，**待确认** AOT 是否同样规范化。
- **根因分析**：用 identity 做池 key 是实现细节层面的乐观假设。
- **影响范围**：若未来某工具链下不 identical，池对默认构造失效 → 「同文件名、两份内存缓存互相抹 key」（R-02 原始事故）复发；生产路径已被 `AppDependencies.production()` 的显式共享兜住，实际爆炸半径 = 测试与兜底路径。
- **复现 / 验证方式**：本次探针脚本（tearoff_probe.dart）；回归测试 `test/local_store_regression_test.dart` 只覆盖「同一 provider 引用」路径，未覆盖默认路径。
- **【最佳实践】**：池 key 用**语义相等**的标识（`provider.hashCode`——tear-off 的 ==/hashCode 规范保证相等），而不是 identity。
- **【最优方案】**：key 改为 `'${provider.hashCode}|$name'`，并补一条「两次无参构造返回同一实例」的回归测试。成本：1 行 + 1 测试；收益：池的行为从「依赖 VM 实现」变为「依赖语言规范保证」；风险：无（tear-off == 与 hashCode 配套保证）。
- **【最小方案】**：不加改动，只在 local_store.dart 类注释里补一句「依赖 tear-off 规范化，探针 2026-11-05 实测成立」。技术债：假设仍无测试钉住。
- **推荐选择及理由**：【最优方案】——这是把一个已实测成立、但靠实现细节站着的假设，换成语言规范保证，成本一行。

### [P3-C04] 流式响应的 timeout 是 per-event 而非整体（潜在风险）

- **位置**：services/rest_client.dart:159（`await for (... in res.timeout(AppConfig.restTimeout))`）
- **现象 / 触发条件**：`Stream.timeout` 的语义是「相邻事件间隔」超时；慢滴流（每 9s 一个字节）不会被掐断，直到 512KB 上限。
- **根因分析**：三处 `.timeout(restTimeout)` 中请求与响应头两处语义正确，body 读取这处是流间隔语义。
- **影响范围**：轮询层有单飞（`_busy`）保护，最坏情形是一轮轮询被拖长，后续轮询排队；目录抓取偶发慢响应同理。512KB 上限兜住了总量。
- **复现 / 验证方式**：单测用假流每 9s 发一个字节，测整体耗时（当前无上限）。
- **【最佳实践】**：body 读取用「整体截止时间」：`res.listen` 包一层 `Future.timeout(restTimeout * 3)` 或读循环里检查 deadline。
- **【最优方案】**：同【最佳实践】，给 body 读取设整体 deadline（如 15s），超时按失败处理并标记池重建。成本：~15 行；收益：单轮耗时上界确定，轮询节奏可预测；风险：极慢但正常的网络被判失败（免费源场景可接受，轮询层自会重试）。
- **【最小方案】**：不改代码，接受现状（512KB 上限已兜底，触发条件苛刻）。技术债：无——记录该语义即可。
- **推荐选择及理由**：**维持现状**（最小方案的精神）。单飞 + 失败重试 + 512KB 三层已有兜底，整体 deadline 的收益在免费源场景下不抵「误杀慢正常响应」的代价。
